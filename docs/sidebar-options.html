The layers sidebar, three ways

Same map in each: two data layers, one of them a group, an imagery layer, the live feed and the basemap. The question each one answers differently is how much a row should tell you before you click it — and what the panel does when there are thirty rows rather than five.

A · Dense rows

What is there now, tightened. One line per layer, 26 pixels, everything else behind selection. The most rows per screen and the least said about any of them.

B · Cards with a legend strip

One card per layer carrying its actual symbology: the colour ramp for a graduated layer, the feature count, whether a filter is on. The panel becomes the legend.

C · Two-line rows

A middle: the name on one line and what the layer is on the second — geometry, count, date span, whether a filter is on — with the symbol carrying the ramp.

For: twice the information of A for 1.6× the height, and the second line is where the things you actually search for live — the count, the filter, the date span. Against: more visual noise than A when every layer is the same kind.

My recommendation is C. The reason is what you have been running into all afternoon: with A you cannot tell from the panel whether a layer is filtered, how many features it has, or what the imagery layer's date span is — you have to select each one and read the inspector, which is four clicks to answer a question the panel could have answered by existing. B answers all of it and then fits three layers on a screen, which is worse than the problem.

C also has room for the thing A has nowhere to put: a state line. A layer whose tiles are failing, whose filter matches nothing, or whose source is a WMS that has stopped answering can say so on its second line, in colour, without a dialog. That is most of the difference between software that feels finished and software that goes quiet when something breaks.
